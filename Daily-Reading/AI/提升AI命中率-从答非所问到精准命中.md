## 一、先厘清概念：你说的"命中率低"到底是哪一种？

很多人把"AI 不准"笼统叫"命中率低"，但实际上它们是 **三种完全不同的问题**，诊断方法和解法都不一样。先对号入座，再对症下药。

### 1.1 三种"命中率"

| 类型 | 表现 | 本质问题 | 举例 |
|------|------|---------|------|
| **① 回答准确率** | 答非所问、胡说八道、漏点 | 指令不清 / 上下文不足 / 模型能力不够 | 问"报销流程"，回答了一堆请假制度 |
| **② 工具/动作命中率** | 该调 A 工具却调了 B，或参数填错 | 工具描述差 / 参数 schema 不严 / 路由不准 | 该查数据库却去搜网页；日期传成字符串 |
| **③ 检索命中率** | RAG 没召回相关资料，导致回答无依据 | 分块不合理 / embedding 不准 / top-k 不当 | 问"2026 年新规"，召回的全是 2023 年旧文档 |

### 1.2 还有一个容易混淆的：缓存命中率

> ⚠️ 注意：**缓存命中率（Cache Hit Rate）** 是另一个维度的概念，它影响的是 **成本和延迟**，不是准确率。
>
> - **Prompt Cache / KV Cache**：缓存 prompt 前缀的 KV 计算，命中则省算力、降延迟。
> - **语义缓存（Semantic Cache）**：相似问题命中历史回答，直接返回。
> - 缓存命中率高 → 又快又便宜；缓存命中率低 → 慢且贵，但 **不会让 AI 答错**。

**所以"命中缓存低"和"命中率低"是两件事：**

```
命中率低（准确率）  →  AI 答错 / 做错   →  这是"质量"问题，本文重点
缓存命中率低        →  AI 慢 / 贵       →  这是"性能"问题，见第七节
```

如果你接入项目后发现"AI 经常做错事"，你要解决的是 **准确率命中率**，下面 2~6 节都是为它服务的。如果你同时想降本提速，再看第 7 节。

### 1.3 30 秒自查：你的项目属于哪一种？

```text
你的 AI 出错时，最常见的现象是？

A. 回答内容不对 / 编造 / 漏信息          → ① 回答准确率问题（看 2.1、2.2、3.1、3.2）
B. 调用了错误的工具 / 参数填错 / 流程走错  → ② 工具命中率问题（看 2.3、2.4、3.4、3.5）
C. 引用的资料不对 / 没找到该找的文档       → ③ 检索命中率问题（看 2.5、3.3）
D. 同样的问题时好时坏，不稳定              → 采样参数 + 缺乏反馈闭环（看 2.6、2.7、3.6）
```

## 二、命中率低的 7 大根因

### 2.1 上下文不足或污染（最常见，占 50% 以上）

LLM 是"短期记忆"生物，**它只能基于你这次喂给它的内容回答**。常见问题：

- **没给上下文**：让 AI"分析这个数据"，却不告诉它数据含义、业务背景、分析目标。
- **上下文过载**：把整个代码库 / 整份文档全塞进去，关键信息被稀释，AI 抓不住重点。
- **上下文过期**：对话太长，早期的规则和约束被"遗忘"，AI 开始自由发挥。
- **上下文矛盾**：多个来源信息冲突，AI 随机选一个。

> 🔑 **核心认知**：2025-2026 年社区共识是 **Context Engineering（上下文工程）比 Prompt Engineering 更重要**。Prompt 是"怎么说"，Context 是"给什么材料说"。材料给错了，话说得再漂亮也白搭。

### 2.2 指令模糊、任务边界不清

```text
❌ "帮我分析一下这个项目"
   → AI 不知道分析什么维度、要什么格式、给谁看

❌ "优化这段代码"
   → 优化性能？可读性？还是重构？AI 只能猜

✅ "分析这个项目的目录结构，按'分层是否清晰、职责是否单一、是否有循环依赖'
   三个维度输出表格，每条给出具体文件路径和改进建议"
   → 边界清晰、维度明确、格式确定
```

**模糊指令 = 让 AI 猜 = 命中率靠运气。**

### 2.3 检索质量差（RAG 场景特有）

RAG 命中率低，几乎都出在这几个环节：

```
文档 → 分块 → 向量化 → 检索 → 排序 → 喂给 LLM
       ↑        ↑        ↑       ↑
     分块太大  embedding  top-k  没 rerank
     语义断裂  模型太弱   太多噪声 精排缺失
```

典型坑：
- **分块按字符数硬切**：一句话被切成两半，语义断裂。
- **embedding 模型与领域不匹配**：用通用模型嵌入专业术语，相似度算不准。
- **只做向量检索**：关键词、专有名词、编号类查询，向量检索反而不如 BM25。
- **没有 rerank**：召回 20 条，前 3 条不是最相关的，LLM 被噪声带偏。

### 2.4 工具描述差、参数 schema 不严（Agent 场景特有）

LLM 调工具靠的是 **工具的描述文字**。描述写得烂，模型就乱调：

```text
❌ 工具名: do_stuff
   描述: 处理一些东西
   参数: data (string)

✅ 工具名: query_order_by_user
   描述: 根据用户 ID 查询该用户最近 30 天的订单列表，
        返回订单号、金额、状态。仅支持查询，不支持修改。
        当用户问"我的订单"或"消费记录"时使用。
   参数:
     user_id (string, 必填): 用户唯一标识，格式为 U 开头 + 9 位数字，如 U123456789
     days (int, 选填, 默认 30): 查询天数，范围 1-90
```

差距在于：**名字表意、描述说清"什么时候用 / 不用什么用"、参数有格式约束**。模型选错工具，70% 是描述没写清楚。

### 2.5 模型能力与任务不匹配

- 让 7B 小模型做复杂多步推理 → 必然出错。
- 让不支持 function calling 的模型调工具 → 参数乱填。
- 让短上下文模型读 10 万字文档 → 中间内容直接"失忆"。

**不是模型不行，是任务选错了模型。**

### 2.6 缺乏反馈闭环

AI 错了 → 你口头骂一句 → 下次它还错。因为没有：
- **评测集**：不知道"命中率"具体是多少，全凭感觉。
- **错误样本回流**：错过的 case 没沉淀成规则或 few-shot。
- **持续校正**：没有把"上次怎么错的、该怎么改"写回系统提示或规则文件。

> 这是人和 AI 协作最关键的差距：**人犯过的错会记住，AI 不会，除非你写下来喂给它。**

### 2.7 输出非结构化 + 解析脆弱

让 AI 自由输出自然语言，再用正则/字符串解析提取关键字段 —— 一旦格式飘了就解析失败，看起来像"命中率低"，其实是 **契约不严**。

```text
❌ "请返回用户的姓名、年龄、邮箱"   → AI 随意排版，解析经常崩

✅ "请严格按以下 JSON Schema 返回，不要有任何额外文字"
   { name: string, age: int, email: string }
```

## 三、提升命中率的核心方法论

把 7 大根因反过来，就是 7 大解法。下面按"性价比从高到低"排序。

### 3.1 上下文工程（投入产出比最高）

**黄金公式：**

```
高质量上下文 = 正确的材料 + 正确的顺序 + 正确的时机 + 及时的清理
```

四条原则：

1. **显式引用，不要让 AI 猜**
   - 用 `@file`、`@folder` 主动喂文件，而不是"你看一下那个文件"。
   - 把关键约束、定义、规则放在系统提示最前面。

2. **分层管理**
   - 全局规范 → 规则文件（`CLAUDE.md` / `.cursorrules` / 系统提示）
   - 任务上下文 → 当前对话
   - 即时材料 → RAG 检索结果
   - 不要把所有东西都堆进对话。

3. **及时清理**
   - 上下文窗口接近上限就开新对话。
   - 用 Git 历史 / 文档代替长对话记忆。

4. **活文档维护**
   - 每次 AI 犯错被纠正，把教训写回规则文件。
   - 这是你项目的"AI 错题本"，越攒越准。

**上下文优先级（从高到低）：**

```
1. 当前任务的明确指令
2. 与任务直接相关的代码/文档（精确引用）
3. 项目级规范和约束
4. Few-shot 示例
5. 对话历史（最近优先）
─────────────────────
↓ 以下尽量少给或清理 ↓
6. 模糊的背景介绍
7. 无关的历史对话
```

### 3.2 指令工程（Prompt Engineering）

把模糊指令变成 **结构化指令**，套这个模板：

```text
【角色】你是一个 {领域} 专家。
【任务】{一句话说清要做什么}
【输入】{给出哪些材料/数据}
【约束】
  - 必须基于给定材料，不能编造
  - 不确定时先问我，不要猜
  - 输出格式：{JSON / 表格 / Markdown}
【输出格式】
  {给出确切的字段或模板}
【示例】
  输入: ...
  输出: ...
```

进阶技巧：

| 技巧 | 适用场景 | 说明 |
|------|---------|------|
| **Few-shot** | 格式难统一、边界模糊 | 给 2-3 个正确示例，命中率立竿见影 |
| **CoT（思维链）** | 多步推理、计算 | 让 AI "先想再答"，`一步步分析` |
| **Self-Consistency** | 推理不稳定 | 采样多次取多数答案 |
| **ReAct** | Agent 决策 | Thought → Action → Observation 循环 |
| **角色锚定** | 容易跑题 | 开头钉死角色和边界 |

> ⚠️ **避坑**：不要堆砌"你是最聪明的、请认真思考"这类空话。模型不会因为你夸它就更准，反而占上下文。每句话都要有信息量。

### 3.3 检索工程（RAG 命中率优化）

RAG 命中率提升是一条流水线，每一步都能榨出几个点：

```
查询改写 → 混合检索 → Rerank 精排 → 上下文压缩 → 引用溯源
   ↑          ↑           ↑            ↑           ↑
 +30%      +15%        +20%        +10%       可解释
```

**① 查询改写（Query Rewriting）**
- 用户原问题往往口语化、缺主语，先让 LLM 改写成清晰检索 query。
- **HyDE**：先让 LLM 假设一个答案，用答案去检索（对长尾问题特别有效）。
- **多查询**：一个问题生成 3 个变体，分别检索后合并去重。

**② 混合检索（Hybrid Search）**
- 向量检索（语义）+ BM25（关键词）+ 元数据过滤。
- 编号、人名、专有名词走 BM25；语义相似走向量。
- 加权融合（如 RRF 算法）效果最稳。

**③ Rerank 精排**
- 召回 20~50 条，用 cross-encoder 模型（如 bge-reranker）重排，取 top 3~5。
- **这一步通常是 RAG 命中率提升最大的一刀**，性价比极高。

**④ 分块策略**
- 按语义分块（标题/段落）而非固定字数。
- 重叠窗口（overlap 10-20%）防止语义断裂。
- 长文档用"父子分块"：检索小块，召回时返回大块上下文。

**⑤ Embedding 模型选择**
- 中文场景：bge-m3、Qwen3-Embedding 等。
- 专业领域：用领域语料微调，或换用领域适配模型。
- 定期评估召回率（Recall@k）。

**⑥ 引用溯源**
- 让 LLM 输出时标注每句话来自哪个文档片段。
- 既提升可信度，又方便人工排查"为什么答错"。

### 3.4 工具/动作设计（Agent 命中率优化）

工具调用的命中率，本质是 **"工具描述 + 参数 schema + 路由策略"** 三件事：

**① 工具描述要写成"使用说明书"**

```text
✅ 好描述的四个要素：
  - 名字：动词_对象，如 get_order_list
  - 作用：一句话说清做什么、返回什么
  - 时机：什么时候该用、什么时候不该用
  - 边界：支持什么、不支持什么、有哪些限制
```

**② 参数 schema 要严格**

```json
{
  "type": "object",
  "properties": {
    "user_id": {
      "type": "string",
      "pattern": "^U\\d{9}$",
      "description": "用户ID，U开头+9位数字"
    },
    "days": {
      "type": "integer",
      "minimum": 1,
      "maximum": 90,
      "default": 30
    }
  },
  "required": ["user_id"]
}
```

用 JSON Schema 约束格式、范围、必填，模型乱填的概率大幅下降。

**③ 工具粒度要适中**
- 太粗：一个工具干十件事，模型不知道什么时候该调。
- 太细：工具太多，模型选不过来。
- 经验值：单职责，5~20 个工具为宜；超过 20 个考虑分层路由或检索式工具选择。

**④ 错误信息要回传给模型**
- 工具执行失败时，把结构化错误信息返回给 LLM，让它自己重试或换工具。
- 不要静默失败，否则模型会"瞎猜"下一步。

### 3.5 结构化输出与校验

**用 function calling / JSON Schema / Pydantic 强制契约：**

```python
from pydantic import BaseModel, Field

class OrderAnalysis(BaseModel):
    order_id: str = Field(description="订单号")
    is_risk: bool = Field(description="是否存在风险")
    risk_reason: str | None = Field(description="风险原因，无风险时为null")
    confidence: float = Field(ge=0, le=1, description="置信度0-1")

# 调用时强制模型返回该结构
result = llm.parse(response_format=OrderAnalysis)
```

**校验 + 重试闭环：**

```
LLM 输出 → Schema 校验
   ├─ 通过 → 使用
   └─ 不通过 → 把校验错误 + 原输出回喂给 LLM → 要求修正 → 重新校验
              （最多重试 2~3 次，仍失败则降级）
```

这一套下来，**解析失败率可以压到 1% 以下**。

### 3.6 反馈闭环与持续优化（长期命中率的关键）

这是把"靠运气"变成"越用越准"的关键：

```
        ┌──────────────────────────────────┐
        │  1. 建评测集（ golden cases ）    │
        │  2. 跑评测，算命中率              │
        │  3. 分析错误样本                  │
        │  4. 改 prompt / 上下文 / 工具     │
        │  5. 错误样本回流成 few-shot/规则  │
        │  6. 重新评测，对比是否提升         │
        └──────────────┬───────────────────┘
                       │ 循环
                       ▼
```

**最小可行做法：**
- 起步只要 20~50 条标注 case，就能算出客观命中率。
- 用 LLM-as-Judge 自动评分（人工抽检 10%）。
- 每次改动都跑一遍评测，知道"改好了还是改坏了"。
- 把高频错误案例写成 few-shot 或系统规则，下次自动避开。

### 3.7 模型与参数选择

- **任务匹配模型**：复杂推理用大模型，简单分类用小模型，省成本又稳。
- **降温度**：需要稳定输出时 `temperature=0` 或 `top_p=0.1`；需要多样性才调高。
- **固定 seed**：便于复现和调试。
- **支持工具调用的模型**：Agent 场景务必用原生支持 function calling 的模型。

## 四、主流 Agent 工具是怎么做的

市场上的成熟 Agent 工具，命中率高的秘诀不是"模型更聪明"，而是 **把上面这套方法论工程化**。看几个代表：

### 4.1 Cursor / Claude Code：上下文工程 + 规则文件 + 小步执行

| 机制 | 做法 | 解决什么 |
|------|------|---------|
| **规则文件** | `.cursorrules` / `CLAUDE.md` 每次自动加载 | 上下文丢失、规范遗忘 |
| **显式引用** | `@file` `@folder` 精确喂上下文 | 上下文污染、猜文件 |
| **小步执行** | 一次只做一个 Step，做完就测就 commit | 上下文过载、出错难回滚 |
| **活文档** | 错误教训写回规则文件 | 缺乏反馈闭环 |

> 核心思想：**不让 AI 一次干太多，用文档和 Git 替代对话记忆。**

### 4.2 Devin / Manus：规划-执行-校验闭环

```
Plan（规划）→ Execute（执行）→ Verify（校验）→ Reflect（反思）
    ↑                                              │
    └──────────── 失败则回到规划 ────────────────────┘
```

- **强制先出计划再动手**，避免一上来乱写。
- **每步执行后校验**（跑测试、看结果），错了自动回退。
- **反思机制**：把失败原因记下来，下步绕开。

这是把 3.6 节的反馈闭环做进了 Agent 内核。

### 4.3 LangChain / LangGraph：结构化状态机

- 用 **图（Graph）** 定义 Agent 流程，每个节点职责单一。
- **State** 在节点间显式传递，避免上下文丢失。
- **条件边** 控制"调哪个工具"，比纯 prompt 路由稳定得多。
- 工具调用结果结构化存入 state，下一步可读可校验。

> 核心思想：**用代码控制流替代"让模型自由发挥"，把不确定的部分框死在节点里。**

### 4.4 Dify / Coze：RAG + 工作流 + 知识库

低代码 Agent 平台的命中率优化，几乎都做了这几件事：
- **知识库**：分块、embedding、混合检索、rerank 全可视化配置。
- **工作流编排**：把复杂任务拆成节点，每节点单一职责。
- **意图识别节点**：先分类再路由，避免一个 prompt 干所有事。
- **变量与上下文管理**：显式声明每个节点的输入输出。

### 4.5 OpenAI Agents SDK / Anthropic MCP：工具协议标准化

- **Function Calling**：原生结构化工具调用，参数 schema 强约束。
- **MCP（Model Context Protocol）**：统一工具/资源/提示的接入协议，工具描述标准化。
- **Handoff**：多 Agent 协作时，显式传递上下文，避免信息丢失。

### 4.6 共同模式总结

不管哪家，命中率高的 Agent 都遵循这 5 条规律：

| 规律 | 体现 |
|------|------|
| **上下文工程优先** | 规则文件、显式引用、状态管理 |
| **任务拆小、单一职责** | 小步执行、工作流节点、状态机 |
| **结构化契约** | Function calling、JSON Schema、State |
| **校验 + 反馈闭环** | 测试、Verify、错误回流、活文档 |
| **检索质量投入** | 混合检索、rerank、知识库 |

## 五、实战落地：一套可复用的优化流程

接到"AI 命中率低"的投诉，按这个流程走，不会乱：

### 5.1 五步优化流程

```
Step 1  诊断  →  对号入座（1.3 自查），定位是回答/工具/检索哪种
Step 2  量化  →  拉一批错误 case，算出当前命中率基线
Step 3  定位  →  逐条分析错因，归类到 2.x 的根因
Step 4  优化  →  按 3.x 对应方法改，每次只改一个变量
Step 5  验证  →  跑评测集对比，提升则保留，否则回滚
         ↑                                       │
         └───────────── 持续循环 ─────────────────┘
```

### 5.2 命中率优化 Checklist

照着勾，勾完命中率不会差：

**上下文（ ）**
- [ ] 是否有项目级规则文件并被自动加载
- [ ] 是否用显式引用（@file / 检索结果）喂关键材料
- [ ] 上下文是否分层（全局/任务/即时）
- [ ] 长对话是否及时清理或开新会话

**指令（ ）**
- [ ] 任务是否一句话能说清边界
- [ ] 是否给了输出格式约束
- [ ] 是否提供了 2-3 个 Few-shot 示例
- [ ] 复杂任务是否用 CoT 拆步

**检索（RAG 场景）（ ）**
- [ ] 分块是否按语义而非字数
- [ ] 是否用了混合检索（向量 + BM25）
- [ ] 是否加了 rerank 精排
- [ ] embedding 模型是否适配领域
- [ ] 是否做了查询改写

**工具（Agent 场景）（ ）**
- [ ] 工具名是否动词_对象、表意清晰
- [ ] 描述是否说清"何时用/何时不用"
- [ ] 参数是否有 JSON Schema 约束
- [ ] 工具数量是否在 5-20 个合理区间
- [ ] 工具错误是否回传给模型

**输出与校验（ ）**
- [ ] 是否用结构化输出（function calling / Pydantic）
- [ ] 是否有校验 + 重试闭环
- [ ] 是否有引用溯源

**反馈闭环（ ）**
- [ ] 是否有评测集（哪怕 20 条）
- [ ] 是否每次改动都跑评测
- [ ] 错误样本是否回流成规则/few-shot
- [ ] 是否维护"AI 错题本"

## 六、让 AI 自己来提升命中率（自动化优化）

> 前面五节讲的都是"人怎么把 AI 调准"。这一节更进一步：**把"诊断-改写-评测-回流"这套流程本身也交给 AI 自动跑**，也就是 "用 AI 优化 AI"（Meta-Optimization）。
>
> 这是 2025-2026 年命中率工程的最新趋势：你不再手动调 prompt，而是搭一个"优化 Agent"，让它持续盯着命中率指标、自动改 prompt / 改检索 / 改工具描述、自动评测、自动沉淀。

### 6.1 核心思路：Optimizer-Critic 双 Agent 闭环

把优化任务拆成两个角色，让它俩互相博弈：

```
┌──────────────────────────────────────────────────────────┐
│                  自动化命中率优化闭环                       │
│                                                          │
│   错误样本 / 评测集                                        │
│        │                                                 │
│        ▼                                                 │
│   ┌──────────┐   改写后的 prompt/工具/检索策略            │
│   │ Optimizer│ ──────────────────────────┐              │
│   │ (优化者)  │                            │              │
│   └──────────┘                            ▼              │
│        ▲                            ┌──────────┐         │
│        │ 哪里差/怎么改               │  Critic  │         │
│        └────────────────────────────│ (评审者) │         │
│                                     └──────────┘         │
│                                          │               │
│                                  跑评测集/LLM-as-Judge    │
│                                  给出分数 + 错因          │
└──────────────────────────────────────────────────────────┘
        ↑                                        │
        └────────── 持续迭代（每轮只改一处）──────┘
```

- **Optimizer**：根据 Critic 的反馈，提出"改 prompt 哪一句 / 换哪个分块策略 / 改哪个工具描述"。
- **Critic**：跑评测集，用 LLM-as-Judge 打分，定位错因，告诉 Optimizer 下一步该改哪。
- **人**：只做最后审核——决定改动能不能合并进生产。

> 关键纪律：**每轮只改一个变量**，否则无法归因"是改 prompt 起的作用还是改检索起的作用"。

### 6.2 让 AI 自动做诊断（命中率医生）

把第三、五节的人工诊断流程，变成一个 prompt 交给 AI：

```text
【角色】你是命中率诊断专家。
【输入】
  - 用户原问题
  - 实际喂给模型的上下文 / 检索结果 / 工具描述
  - 模型实际输出
  - 期望输出（golden answer）
【任务】按以下维度归因，每条给出"是/否/证据"：
  1. 上下文不足：期望信息是否在喂入材料中存在？
  2. 上下文污染：是否有矛盾/噪声误导模型？
  3. 指令模糊：任务边界、输出格式是否清晰？
  4. 检索失误：召回片段是否包含答题所需信息？
  5. 工具选择错误：是否选错工具或参数填错？
  6. 输出契约失效：格式是否被破坏？
  7. 模型能力不足：是否需要更强模型？
【输出】
  - 主因（1 个）
  - 次因（0-2 个）
  - 具体改进建议（可执行，如"在系统提示第 3 行加入 X 约束"）
```

跑一遍所有错误 case，自动归类成"上下文问题 N 条、指令问题 M 条……"，下一步该攻哪个根因一目了然。

### 6.3 让 AI 自动改写 Prompt（Meta-Prompting）

不用人想措辞，让 AI 自己优化自己的 prompt：

```text
【任务】你是一个 prompt 优化器。
【当前 prompt】
  {当前系统提示全文}
【评测结果】
  - 命中率：62%
  - 典型错误：
    1. 输入 X，期望 Y，实际输出 Z（错因：编造了不存在的字段）
    2. 输入 A，期望 B，实际输出 C（错因：未遵循 JSON 格式）
【优化规则】
  - 只改一处，保留有效部分
  - 优先用"约束 + 示例"解决，不要堆形容词
  - 输出新 prompt 全文 + 改动说明（改了哪、为什么）
  - 不要删除原有约束，只能新增或收紧
【输出】
  new_prompt: ...
  change_summary: ...
  expected_impact: ...
```

**市场工具参考：**

| 工具 | 思路 | 适用 |
|------|------|------|
| **DSPy** | 把 prompt 当作可学习参数，用示例自动编译出最优 prompt | RAG / 分类 / 抽取 |
| **TextGrad** | 把 LLM 反馈当"梯度"，反向传播回 prompt 各部分 | 复杂推理任务 |
| **Promptbreeder** | 用进化算法让 prompt 自我变异、择优 | 通用任务 |
| **ADPE（自动提示工程）** | 用一个元模型生成候选 prompt，另一个打分择优 | 自动化评测闭环 |

落地最小可行版：**不用上框架，直接写两个 prompt + 一个评测脚本**，就能跑出"自动改 prompt → 评测 → 保留/回滚"的闭环。

### 6.4 让 AI 自动优化检索（RAG 自调优）

检索链路的每个环节都能让 AI 自动调：

| 环节 | AI 自动做的事 |
|------|--------------|
| **查询改写** | 让 LLM 把口语问题改写为检索 query，再生成 3 个变体 |
| **分块策略** | 让 AI 评估"按段落分 vs 按标题分"哪个召回率高，自动选优 |
| **embedding 适配** | 让 AI 标注一批"难例"，用于微调或选型对比 |
| **rerank 调参** | 让 AI 调 top-k、权重、阈值，跑评测对比 |
| **混合检索权重** | 让 AI 在"向量 vs BM25"权重上做网格搜索 |

**自调优 RAG 的闭环脚本（伪代码）：**

```python
def auto_tune_rag(eval_set, candidates):
    """
    eval_set: 标注好的评测集
    candidates: 候选配置（分块策略/embedding/rerank/top-k 的组合）
    """
    results = []
    for config in candidates:
        score = run_eval(eval_set, rag_pipeline=config)
        # 让 AI 分析低分 case 的错因
        errors = collect_failures(eval_set, config)
        diagnosis = llm_diagnose(errors)  # 调 6.2 的诊断 prompt
        results.append({config, score, diagnosis})

    best = max(results, key=lambda r: r.score)
    # 让 AI 基于最佳配置的错因，提出下一轮候选
    next_candidates = llm_propose_configs(best, results)
    return best, next_candidates  # 人审核后进入下一轮
```

关键：**不让 AI 自己判断"准不准"**，而是用评测集的客观分数当裁判，AI 只负责"归因 + 提方案"。

### 6.5 让 AI 自动生成/优化工具描述

Agent 工具命中率低，多半是描述写得烂。让 AI 反向帮你写：

```text
【任务】根据下面的工具代码，反推一个高质量的函数描述。
【代码】
  {函数签名 + 实现 + 注释}
【输出要求】
  1. 工具名：动词_对象，清晰表意
  2. 描述：包含"做什么 / 返回什么 / 何时用 / 何时不用 / 限制"
  3. 参数 JSON Schema：带 type / required / 格式约束 / description
  4. 1 个调用示例 + 1 个不该调用的反例
【自检】
  - 读你的描述，能否 100% 判断"该不该调这个工具"？
  - 参数格式是否够严，模型乱填会失败？
```

进一步：**让 AI 当"工具路由测试员"**，造一批"该调 A 不该调 B"的边界 case，自动跑工具选择评测，命中不够就把这些反例作为 few-shot 加进系统提示。

### 6.6 让 AI 自动维护"错题本"和规则文件

这是把"持续优化"变成"无人值守"的关键：

```
真实线上错误
    │
    ▼
AI 自动归因（6.2 诊断 prompt）
    │
    ▼
AI 提炼"规则/few-shot/约束"
    │
    ▼
人审核 → 合并进规则文件 / 系统提示
    │
    ▼
自动跑评测验证不回退
    │
    ▼
发布
```

- 每次线上 AI 答错（用户点踩 / 人工标注错），自动触发诊断 + 提炼规则。
- 规则以"补丁"形式追加到 `CLAUDE.md` / 系统提示的"已知坑"段落。
- 追加后自动跑回归评测，确认不破坏其他 case 才合并。

> 这就是 Cursor 推荐的"活文档"思路的自动化版本：**让 AI 自己把错题写回规则文件**，越用越准，不用人手动维护。

### 6.7 让 AI 自动优化缓存命中率

缓存命中率也能让 AI 自动调，思路是让 AI **重排 prompt 前缀**：

```text
【任务】你是 prompt 缓存布局优化器。
【输入】
  - 当前 prompt 各部分：系统提示 / 规则 / few-shot / 知识库 / 用户输入
  - 各部分在最近 100 次请求中的"变化频率"（0-1）
【目标】最大化 Prompt Cache 命中率。
【规则】
  - 变化频率低的部分排前面（稳定前缀）
  - 变化频率高的部分排后面（易变后缀）
  - 同一会话内尽量复用相同前缀
  - 时间戳/会话ID/用户输入必须放最后
【输出】
  - 重排后的 prompt 布局
  - 预估缓存命中率提升
  - 需要稳定的部分（建议固化成模板）
```

进阶：让 AI 自动识别"哪些片段可以抽成稳定前缀模板"，把易变部分参数化，长期下来缓存命中率会显著上升。

### 6.8 落地范式：三种自动化程度，按需选

| 程度 | 做什么 | 适合 |
|------|--------|------|
| **L1 半自动（推荐起步）** | AI 诊断 + 提建议，人审核后手动改 | 任何团队，立刻能上 |
| **L2 辅助自动** | AI 诊断 + 改写 + 跑评测，人只做"合并/回滚"决策 | 有评测集的中型项目 |
| **L3 全自动（慎用）** | AI 自动改 prompt/工具/检索 + 自动合并 + 自动发布 | 线上无副作用、可灰度的场景 |

### 6.9 自动化的三条红线

让 AI 自己优化，必须守住这三条，否则越调越烂：

1. **评测集是唯一裁判**：不让 AI 自己说"我改好了"，必须跑客观评测，分数说了算。
2. **防过拟合**：评测集不能太小，否则 AI 会"背答案"。保留一份 hold-out 集做最终验证。
3. **防 reward hacking**：警惕 AI 学会"钻空子"（比如把不确定的输出都改成空字符串以提高格式通过率）。Critic 要同时看"命中率"和"有用性"，不只看格式。

> 一句话：**让 AI 当工人，让评测当监工，让人当质检员。** 工人可以换，监工不能松，质检员不能省。

## 七、避坑清单

| 坑 | 现象 | 解法 |
|----|------|------|
| **靠感觉调 prompt** | "感觉好点了"但没数据 | 建评测集，用数字说话 |
| **一次改三个变量** | 不知道哪个起作用 | 每次只改一个，对比验证 |
| **疯狂堆上下文** | 全文档塞进去，反而更差 | 精选相关片段，少即是多 |
| **小模型硬扛复杂任务** | 怎么调都不准 | 换大模型或拆解任务 |
| **工具描述写一句话** | 模型乱调工具 | 写成"使用说明书" |
| **自由文本输出再正则解析** | 解析经常崩 | 用结构化输出 |
| **错了不沉淀** | 同样的错反复犯 | 错题本写回规则文件 |
| **只调 prompt 不调检索** | RAG 永远不准 | 检索链路单独评测优化 |
| **temperature 拉满** | 同一问题答案飘 | 需稳定输出时温度调 0 |
| **盲目加 few-shot** | 示例太多反而过拟合 | 2-3 个高质量、覆盖边界 |

## 八、关于"缓存命中率"的补充

如果你确实想优化的是 **缓存命中率**（降本提速），思路完全不同，核心是 **让 prompt 前缀尽量稳定**：

### 8.1 Prompt Caching（前缀缓存）

原理：LLM 推理时把 prompt 前缀的 KV 计算结果缓存，下次相同前缀直接复用。

**提升命中率的关键：把易变内容放后面，稳定内容放前面。**

```text
✅ 高命中率布局：
[系统提示] [规则] [few-shot] [长文档] ... [用户本次问题]
└────────────── 稳定，能缓存 ──────────────┘ └ 易变 ┘

❌ 低命中率布局：
[用户本次问题] [系统提示] [规则] [长文档]
└ 易变 ┘ └──────────────────────────────────┘
   ↑ 第一token就变，后面全缓存失效
```

技巧：
- 系统提示、规则、few-shot、知识库放在最前面。
- 用户输入、时间戳、会话 ID 放最后。
- 同一会话内尽量复用相同前缀。

### 8.2 语义缓存（Semantic Cache）

- 用 embedding 检索"是否问过相似问题"。
- 相似度高于阈值则直接返回历史答案，不再调用 LLM。
- 适合：客服 FAQ、高频重复查询。
- 注意：**语义缓存可能返回过期或错配答案**，对时效性/准确性要求高的场景慎用。

### 8.3 KV Cache 命中率优化

- 控制上下文长度，无关内容及时清理。
- 对话历史按"稳定前缀 + 增量"组织。
- 用支持 prompt cache 的模型（Claude、Gemini、GPT-4o 等都已支持）。

> 🔎 **一句话区分**：缓存命中率高 → **又快又便宜**；准确率高 → **答得对**。前者是性能优化，后者是质量优化，别混为一谈。

## 九、总结

**命中率低不是 AI 笨，是你没把"让 AI 做对"当成工程问题来对待。**

记住这条主线：

```
命中率 = 上下文工程 × 指令工程 × 检索工程 × 工具工程 × 反馈闭环
```

具体到行动：

1. **先诊断**：分清是回答、工具、检索哪种命中率低。
2. **再量化**：拉评测集，算基线，别靠感觉。
3. **对症下药**：
   - 回答不准 → 上下文 + 指令 + 结构化输出
   - 工具错 → 工具描述 + 参数 schema + 错误回传
   - 检索错 → 混合检索 + rerank + 查询改写
4. **建闭环**：错误样本回流，规则文件持续更新，越用越准。
5. **学市场**：Cursor 的规则文件、Devin 的校验闭环、LangGraph 的状态机、Dify 的检索链路 —— 都是同一套方法论的工程化。
6. **再自动化**：把诊断-改写-评测-回流交给 AI 自己跑（第六节），从"人调 AI"升级到"AI 优化 AI"，人只当质检员。

最后一句口诀：

> **材料给对（上下文）+ 话说清楚（指令）+ 找得准（检索）+ 调得稳（工具）+ 错了能改（闭环）= 高命中率。**

至于"缓存命中率"，那是另一个维度的性能优化，布局好 prompt 前缀就能大幅提升，但它解决的是"快不快、贵不贵"，不是"对不对"。
