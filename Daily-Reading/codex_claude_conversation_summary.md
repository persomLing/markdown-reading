# Codex 与 Claude Code 协作对话总结

本总结不包含“大模型能力排名”相关内容，只整理当前对话中关于 Codex 功能、归档/分叉、子代理、Claude Code 协作，以及 520 静态页面实验的讨论。

## 1. 归档、分叉、子代理的区别

### 归档

归档可以理解为“把这条对话收进抽屉”。

它不是删除，而是把当前对话从活跃列表中收起来，让界面更清爽。以后通常仍然可以从历史或归档中找回。

适合归档的情况：

- 当前任务已经结束
- 暂时不需要继续看这条对话
- 聊天列表太乱，需要整理
- 想保留记录，但不想它继续占据主列表

一句话总结：

> 归档就是“收起来，但不丢掉”。

### 分叉

分叉相当于“复制当前对话，开一条新路线”。

它会保留原对话不变，同时基于当前上下文创建一个新线程。适合用于尝试不同方案。

典型场景：

- 同一个需求想试两种实现方式
- 当前对话方向有点乱，想开一个更干净的新分支
- 想保留原来的思路，同时探索另一个方案

### 子代理

子代理更接近“老板模式”里的员工或同事。

主 Codex 可以负责拆任务、分配任务、整合结果；子代理负责探索、实现或验证某个独立部分。

适合使用子代理的情况：

- 大型代码库需要并行分析
- 多个模块可以互不冲突地同时修改
- 一个代理写代码，另一个代理做 review 或测试
- 多个方案需要并行探索

不适合使用子代理的情况：

- 小改动
- 单文件修改
- 必须一步接一步执行的任务
- 需求还没说清楚

## 2. Codex 作为主 Agent，Claude Code 作为 Worker

讨论中确认：可以让 Codex 作为主 agent，调用本机的 Claude Code CLI 作为外部编程 worker。

协作模式大致是：

- Codex 负责分析需求、设计方案、划分任务边界
- Claude Code 负责根据明确任务进行代码实现
- Codex 再审查 Claude Code 的改动，运行验证，必要时修正

这种模式不是让 Codex “控制 Claude 的脑子”，而是通过命令行把 Claude Code 当作一个外部执行者调用。

## 3. 本次 520 静态页面实验

为了验证这种协作方式，实际做了一个简单静态页面：

主题：

> 520 节日送给女朋友的惊喜页面

执行过程：

1. Codex 检查本机是否存在 `claude` 命令。
2. 确认可调用 Claude Code CLI。
3. Codex 生成页面主视觉图，并放入项目目录。
4. Codex 给 Claude Code 下达明确任务，只允许它修改 `520-surprise` 目录。
5. Claude Code 创建了页面初版。
6. Codex 审查后发现两处问题：
   - 页面引用了 Google Fonts 外链，不符合“无外部网络依赖”的要求。
   - 没有实现“点击揭晓隐藏告白”的交互按钮。
7. Codex 直接补上修复：
   - 去掉外链字体，改成本地字体栈。
   - 添加隐藏告白按钮和交互逻辑。
8. Codex 用本地 Chrome + Playwright 验证：
   - 页面标题正常。
   - 主视觉图片加载成功。
   - 点击按钮后隐藏告白可显示。
   - 桌面和移动端截图可正常渲染。

生成的页面目录：

```text
520-surprise/
├── index.html
├── assets/
│   └── hero-520.png
├── desktop-check.png
└── mobile-check.png
```

本地预览服务后来通过 Node REPL 启动，访问地址为：

```text
http://127.0.0.1:8787/
```

## 4. 是否更节约 Token

结论：

> 小任务通常 Codex 单独做更节约 token。

原因是 `Codex + Claude Code` 会多出额外成本：

- Codex 要先分析和写任务说明
- Claude Code 要重新读取上下文并实现
- Codex 要再次读取 Claude 的改动
- Codex 还要审查、测试、修正
- 如果 Claude 做偏，还要返工

对于小型静态页、小 bug、单文件修改，这种双 agent 模式通常不省 token，也不一定更快。

更适合 `Codex + Claude Code` 的情况：

- 大项目
- 多模块并行开发
- 高风险重构
- 需要多个方案并行探索
- 可以清楚划分不同 agent 的文件边界

## 5. 为什么小问题不继续让 Claude Code 修改

本次 Claude Code 初版漏了两点，但 Codex 没有再让 Claude Code 返工，而是直接修复。

原因：

- 问题很小，直接改几行更快。
- 重新启动 Claude Code 需要再次组织提示词。
- Claude Code 修改后仍然需要 Codex 审查。
- 外部 agent 可能顺手改动不该改的内容。
- 主 agent 应该判断派工成本，而不是把所有小问题都转交出去。

更合理的模式：

> 大块实现交给 worker，小修小补由主 agent 直接收尾。

## 6. 是否应该长期维持 Claude Code 会话

讨论中提到：刚才使用的是 `claude -p` 这种一次性非交互模式。

它的特点：

- 每次启动一次 Claude Code。
- 执行完任务后退出。
- 边界清晰，可控性强。
- 适合短任务或明确的 worker 任务。

长期维持 Claude Code 会话理论上可以，但有风险：

- 容易卡在权限确认或交互输入。
- 上下文会漂移。
- 权限边界更难长期维护。
- 本地 CLI 会话可能被系统回收。
- 每次派任务仍然需要重申边界和验收标准。

适合长期会话的情况：

- 连续多步开发
- 同一个 worker 需要持续处理相关任务
- 用户明确要求“我说关闭前不要关闭”

不适合长期会话的情况：

- 小修小补
- 单次任务
- 需要强隔离、强可复现的修改

## 7. 最终经验总结

最实用的判断方式：

| 场景 | 更合适的方式 |
|---|---|
| 小页面、小 bug、单文件修改 | Codex 单独做 |
| 中等功能、需要快速交付 | Codex 单独做，必要时让 Claude Code 做局部 worker |
| 大型代码库、多模块并行 | Codex 主控 + Claude Code / 子代理 |
| 高风险重构 | 多 agent 分析，主 agent 最终整合 |
| 需求还不清楚 | 先由 Codex 澄清和设计 |

一句话总结：

> Codex 更适合做主控、设计、审查和收尾；Claude Code 更适合做明确边界内的大块实现。小任务不要为了“老板模式”而强行派工。
